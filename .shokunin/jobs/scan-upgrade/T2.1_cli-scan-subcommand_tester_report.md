## Design followed (per JOB.md "Design imposé par le CTO" — not improvised)

- **Dependency injection, no mock HTTP server.** All new tests inject
  `{ scan: mockScanFn }` into `runCli(argv, { scan })`, exactly mirroring the
  existing `{ validate }` pattern. No `node:http`/`sirv` server started for
  any scan test.
- `CliScanRunner` and `ScanOptions`/`ScanOutcome` types imported (type-only)
  from `./cli`, `./types`, `./scan` — `CliScanRunner` does not exist in
  `cli.ts` yet (expected; esbuild/vitest strips type-only imports without
  checking against real exports, so the file still transforms and runs).
- Argv shape used throughout: `['scan', '<url>', ...flags]`.
- JSON stdout contract asserted as an **exact string equality**:
  `` `${JSON.stringify(outcome.status, null, 2)}\n` `` — the raw `ScanStatus`,
  never enriched, never re-derived.
- Human summary (no `--json`) asserted via minimal, explicit "Label: value"
  strings consistent with the project's existing `formatHumanResult`
  convention (`Score: 82`, `Verdict: good`, `P0: 1`, `P1: 1`, `P2: 0`), plus a
  check that stdout does not start with `{` (not raw JSON). Exact wording was
  not dictated by the JOB (only "au minimum url, score, verdict, findings par
  sévérité"), so these are the Tester's pinned acceptance strings — the Coder
  must match them or the test stays red for a legitimate reason.
- stderr always asserted to contain `outcome.auditLinks.terminal` and never
  `outcome.auditLinks.html`, for both `--json` and non-`--json` runs (fixture
  gives the two links distinct, non-substring query values so the assertion
  is meaningful).
- `--api-key` asserted as a true no-op: same captured `ScanOptions` (minus the
  `onProgress` function reference, stripped before comparison) with and
  without the flag, and no `apiKey` property leaking onto the options object.
- `--html` minimal write asserted to contain `url` and
  `outcome.auditLinks.html`, and explicitly **not** `auditLinks.terminal`.
- Invalid `--html` (empty, non-`.html`) asserted to error before `scan` is
  ever invoked (`scanCalls === 0`), reusing the exact existing
  `validateHtmlPath` error strings (`HTML report path must not be empty` /
  `must end with .html`), since the JOB says this logic is reused, not
  duplicated.
- Failure pass-through (`ScanFailedError`, `ScanRequestError`,
  `ScanTimeoutError`) asserted with `exitCode !== 0` (not hardcoded to `2`,
  matching the JOB's own wording), `stdout === ''`, `stderr` contains the raw
  error message, and — for the two `--html` cases — the report file is
  confirmed absent via a `fileExists` helper (`stat` + catch).
- `onProgress` asserted to write `Scan progress: fetch` then
  `Scan progress: render` to stderr, in that order (`indexOf` comparison),
  and never to stdout (`--json` mode keeps stdout pure JSON).
- `--timeout <ms>` asserted forwarded verbatim to
  `capturedOptions.timeoutMs`.

## 11 new tests written (cover all 10 minimum cases in JOB.md; case 3 and
case 6 each folded into one test asserting both sub-conditions)

1. `prints the raw scanner status as JSON for scan --json`
2. `prints a compact human summary for scan without --json`
3. `always prints the terminal audit link on stderr after a done scan, with or without --json`
4. `accepts --api-key without forwarding it to scan options`
5. `writes a minimal HTML report and keeps stdout JSON-only for scan --json --html`
6. `rejects an invalid --html path before ever calling scan`
7. `fails cleanly and writes no HTML report when scan rejects with ScanFailedError`
8. `fails cleanly and writes no HTML report when scan rejects with a scanner transport error` (`ScanRequestError`)
9. `fails cleanly when scan rejects with a poll timeout error` (`ScanTimeoutError`)
10. `writes scan progress steps to stderr in order and never to stdout`
11. `forwards --timeout to ScanOptions.timeoutMs`

New fixtures added (module-scope, alongside the existing `validationResult`
helper): `scanStatusDone`, `scanOutcome`, `omitOnProgress`, `fileExists`.

All 11 failures share the same root cause: Commander currently has no `scan`
subcommand, so argv `['scan', 'https://example.com', ...]` is parsed against
the existing single `<url>` positional argument, producing
`error: too many arguments. Expected 1 argument but got 2: scan,
https://example.com.` → `exitCode: 2`. This is the correct and expected red
state for TDD at this stage — every failure is a manifestation of "the `scan`
subcommand does not exist yet," not a bug in the test assertions themselves.
All 24 pre-existing `validate` tests, and all other 118 tests across the
package's other 13 test files, remain green — zero regression introduced by
extending the file.
