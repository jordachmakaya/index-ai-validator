# Report — T2.0_scan-orchestrator (coder)

## Implémentation

- `packages/validator/src/types.ts` (extension) : ajout de `ScanOptions`
  (import de `ScanProgressStep` depuis `./client/scanner-client`, aucun autre
  type existant touché).
- `packages/validator/src/scan.ts` (nouveau, `@filemeta` en tête) :
  - `type ScanOutcome = { status: ScanStatus; auditLinks: { html: string; terminal: string } }`
  - `class ScanFailedError extends Error` — `readonly code: string`, message
    dev-friendly citant le code, renvoyant vers le registre SCAN-NNN de
    `CONTRACT_SCANNER.md` et suggérant un re-scan.
  - `async function scanUrl(options)` : `submitScan` → si terminal (`done`/`failed`)
    retour direct, sinon `pollScan` (jamais les deux). `failed` → lève
    `ScanFailedError(status.failureReason ?? 'SCAN-UNKNOWN')`. `done` → retourne
    `{ status, auditLinks }` sans muter `status`. Aucun `try/catch` : les
    erreurs `ScanRequestError`/`ScanTimeoutError` etc. traversent telles quelles.
  - Deux petits helpers privés (`buildSubmitOptions`, `buildPollOptions`)
    construisent les options en omettant les clés `undefined`, requis par
    `exactOptionalPropertyTypes` (même idiome que `fetchScan` dans
    `scanner-client.ts`). `onProgress` est transmis par identité (pas de wrapper),
    avec un cast ciblé et commenté vers le type plus large déclaré côté
    `PollScanOptions` (`{ currentStep: string }` vs `ScanProgressStep`).

Aucune nouvelle dépendance. Skills invoqués : `engineering-rules`, `shokunin`,
`shokunin-filemeta`.
