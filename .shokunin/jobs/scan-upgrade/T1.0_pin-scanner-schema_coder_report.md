## Schema / validation approach

- Root schema: `required: [url, score, verdict, dimensions, findings, noiseRatio, engineVersion, schemaVersion]`, `additionalProperties: true` — tolerant reader per contract §6 rule 4 (verified by test: unknown sibling field `newField` does not raise an error).
- `score`: `integer`, `minimum: 0`, `maximum: 100`.
- `schemaVersion`: `{ "const": "1.0" }` — a mismatch (`"2.0"`) produces AJV keyword `const` at `/schemaVersion`, never `required`, and is absent entirely when `schemaVersion` is valid but another field is missing (test 5 checks both).
- **`dimensions` — exactly the 5 keys in fixed order.** Judgment call: rather than `minItems`/`maxItems` + `enum` + `contains` (which would allow duplicates/permutations to slip through undetected structurally), I used AJV draft-07 **tuple validation**: `items` as an array of 5 positional schemas, each pinning `key` to a `const` (`access`, `extractability`, `citability`, `safety`, `agent_layer` in that order) plus `minItems: 5`, `maxItems: 5`, `additionalItems: false`. This directly encodes the contract's "TOUJOURS les 5, ordre fixe" rule and makes duplicate/out-of-order/missing keys structurally impossible to pass, not just discouraged. AJV's default export (`ajv@8.20.0`) validates against draft-07 by default (no `$schema` keyword needed, consistent with how `manifestSchema`/`graphSchema` are already written in this file), where array-form `items` is tuple syntax — this matches the existing codebase convention (inline `as const` schema objects, no `$schema` field).
- `findings`: array of `{ id, severity: enum P0/P1/P2, title }` required, `detail`/`effort` optional, `additionalProperties: true`.
- `noiseRatio`: `type: ["number", "null"]` (required, nullable). `csrGapPercent`: same type, optional. `renderedComparison`: optional object requiring `status` enum.
- **Required-field error path (`/score`).** Judgment call: standard AJV behavior reports a `required` error's `instancePath` as the *parent object's* path, not the missing field's path (this is what the existing graph tests already rely on — e.g. `/nodes/0/content` with `keyword: 'required'` for a missing `summary_method`, and I did not touch that behavior). But `schemas.test.ts` test 2 explicitly expects `path: '/score'` for a root-level missing field. To satisfy both without weakening the graph/manifest tests' existing convention, I added an **opt-in** parameter to the shared `formatAjvErrors(errors, options?)`: `appendMissingPropertyToRequiredPath`. Default (`undefined`/omitted) preserves the exact prior behavior — `validateManifestSchema` and `validateGraphSchema` call `formatAjvErrors(validate.errors)` unchanged. `validateScanResult` opts in, appending `params.missingProperty` to `instancePath` only for `keyword === 'required'` errors, turning `''` (root) into `/score`. This is DRY (one shared formatter, no duplicated mapping logic) and additive (zero behavior change for the two existing callers).
