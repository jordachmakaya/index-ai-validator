### 5. 429 retry: exactly 1x, respects `Retry-After`, no exponential backoff

`performScanRequest` (lines 177-197): on a 429, reads `Retry-After` via
`readRetryAfterMs`, drains the first response body, sleeps once, issues
exactly one retry `fetch`, then unconditionally routes the retry's response
(success or a second 429) through `resolveResponseBody` — there is no loop,
no recursive call, no counter that could permit a second retry. A second 429
maps straight to `ScanRateLimitError` via the same `throwForErrorResponse`
switch used everywhere else — not a special "give up after N attempts" branch,
confirming there genuinely is no backoff *engine*, just one bounded retry.
`readRetryAfterMs` (lines 299-308): `Number(header) * 1000`, falls back to
`DEFAULT_RETRY_AFTER_MS` (1000ms) only when the parsed value is `NaN` or
negative — a real `'0'` header is finite and non-negative, so it takes the
"valid header" branch, not the fallback branch (relevant to item 12 below).
**Pass.**

## Independent verdict — `ScanResponseShapeError` addition

**Justified, not scope creep.** It guards exactly one boundary: the raw HTTP
JSON envelope (`scanId`, `status`, `submittedAt`/`completedAt`, `meta.links.*`,
optional `progress`), before any of it is trusted or handed to
`validateScanResult`. This is precisely what `engineering-rules`
("zero-trust input", "réponses HTTP jamais consommées sans vérifier
status/forme") requires for an external HTTP response and is functionally
distinct from — not a duplicate of — the 7 required contract-error classes,
which all represent *server-declared* error states (`code`/`message` from a
`4xx`/`5xx` body). `ScanResponseShapeError` instead represents *client-side
distrust of a nominally-200 envelope's shape*. It does not rename, replace,
or change the shape of any required export; the `@filemeta` `classes:` list
and the coder's own report both flag it as additive. No simpler existing
mechanism in the codebase covers this (the schema-validation machinery in
`schemas.ts` is scoped to `ScanResult`, not the outer `ScanStatus` envelope).
**Verdict: reasonable engineering, not overreach.**

## Independent verdict — test-fix commit (`3c2d9f8`)

**Legitimate fix, still meaningfully proves the 429-retry-once behavior.**
Reasoning, formed independently of the Tester's own framing:

- The root-cause claim (fake `setTimeout` breaking undici's real socket
  internals) is plausible and consistent with the coder's independently-run
  repro described in the Coder report (real-fetch-then-fake-sleep hangs at
  small `advanceTimersByTimeAsync` windows, passes at large ones for an
  unrelated reason). I did not need to re-run the repro to accept this,
  since the observable evidence (both tests time out identically at exactly
  5000ms under fake timers, both pass in single-digit ms under real timers)
  is a strong independent signal that this is a fake-timer/real-socket
  interaction, not a logic bug — and no line in `scanner-client.ts` changed
  between the two states.
- The assertions that matter did not change: `requestCount === 2` in both
  tests is the load-bearing proof of "bounded to exactly one retry, no loop,
  no multi-attempt backoff" — this is untouched.
- Changing `Retry-After` from `'2'`/`'1'` seconds to `'0'` does **not**
  silently switch the code onto its fallback/default path. I checked
  `readRetryAfterMs` directly: the fallback (`DEFAULT_RETRY_AFTER_MS`) only
  triggers on `NaN` or negative values; `Number('0')` is `0`, which is finite
  and non-negative, so the "valid header, respect it" branch
  (`seconds * 1000`) still executes. The test still exercises real
  header-parsing of a real `Retry-After` value, just a fast one.
- What *is* weaker post-fix: with a `0`-second delay, the test can no longer
  distinguish "the client waited approximately the specified duration" from
  "the client didn't wait at all." But the *pre-fix* version didn't
  meaningfully prove that either — advancing a fake clock past a threshold
  only proves the awaited promise resolves after the threshold is crossed
  fake-clock-side, which is a weak proxy for real timing under any
  implementation. Neither version asserts on wall-clock timing directly, so
  nothing of substance was lost.
- Scope discipline: only the 2 named tests changed (verified directly via
  `git show 3c2d9f8`), the file's other fake-timer test (90s budget) and all
  helper functions are untouched, matching both the job's letter and its
  intent.

**Verdict: not a weakening — a correct, minimally-scoped fix to a real
test-environment problem.**

## Non-blocking notes

1. **90s-budget test's proof is weaker than its name implies** (pre-existing,
   inherited unmodified from the original Tester commit `0b0422b`, not part
   of this job's scope of changed files, so not blocking here). Because
   `vi.useFakeTimers()` + a real local-`http` `fetch()` are combined the same
   way that caused the two hangs above, the fake clock likely jumps to +95s
   before the first real (near-instant) `fetch` resolves; the very next
   `Date.now() >= deadline` check then fires immediately. The test genuinely
   proves "`pollScan` eventually rejects with `ScanTimeoutError` and does not
   hang forever" (the real risk it guards against, and the literal checklist
   wording), but does not exercise ~45 real poll iterations at 2s spacing as
   its name suggests. Manual read of `pollScan`'s loop (deadline check every
   iteration, `sleep(intervalMs)` between `running` polls) shows the
   *implementation* is correct regardless; this is a test-depth observation,
   not a code bug. Worth a future look if this test's real intent needs
   stronger proof, but out of this job's changed-files scope.
2. **Minor `User-Agent` drift**: `scanner-client.ts` hardcodes
   `` `${PACKAGE_NAME}/0.1 (+https://agent-view.com)` `` (line 214), but
   `packages/validator/package.json` version is `0.2.0` and `PACKAGE_NAME`
   already includes the npm scope (`@hardmachinelabs/index-ai-validator`),
   so the emitted header reads
   `@hardmachinelabs/index-ai-validator/0.1 (+https://agent-view.com)`,
   diverging from the contract's *recommended* (not required)
   `index-ai-validator/{version} (+https://agent-view.com)` format and from
   the package's real version. `Content-Type`/auth/timeout are all correct;
   this only affects a non-validated, best-effort header. Not blocking —
   contract marks it "recommandé", no test asserts it — but cheap to fix
   later (read version from `package.json` or a constant kept in sync).
3. **Timeout/AbortController boilerplate duplicated** between `http.ts`'s
   `fetchOnce` and `scanner-client.ts`'s `fetchScan` (~15 near-identical
   lines each). Not flagged as a DRY violation to fix in this job: the two
   functions serve genuinely different trust boundaries (`http.ts` fetches
   arbitrary third-party target sites under SSRF policy and streams/truncates
   bodies; `scanner-client.ts` calls one first-party JSON API with POST
   support and 429/Retry-After handling) — and `http.ts` is explicitly
   out-of-scope for this job (checklist item 11). Extracting a shared
   `withTimeout` helper would require touching `http.ts`, which this job
   correctly did not do. Noting for a future, separately-scoped cleanup job,
   not this one.
